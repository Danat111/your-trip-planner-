# بناء الواقع المعزز (AR) الحقيقي — وثيقة معمارية ومشروع فرعي منفصل

## لماذا هذا وثيقة منفصلة؟
الواقع المعزز الحقيقي (وليس رسوماً توضيحية) هو **مشروع هندسي قائم بذاته**،
بحجم وتعقيد قريب من حجم بناء تطبيق الرحلات نفسه. يحتاج فريقاً وخبرات مختلفة
(مطوري iOS/Android أصليين، فنانين ثلاثي الأبعاد، خبير جيومكاني)، ولا يجب خلطه
بخط زمني موقع/تطبيق الرحلات الأساسي. هذه الوثيقة تحدد **ماذا سنبني، وكيف،
وعلى أي مراحل**.

---

## 1. تحديد النطاق: أي ميزات AR سنبني فعلياً؟

التوثيق الأصلي وعد بأربع ميزات. بالترتيب الواقعي من الأسهل إلى الأصعب:

| الميزة | الواقعية التقنية | الجهد التقديري |
|---|---|---|
| **معاينة الوجهة (نماذج 3D ثابتة)** | سهلة نسبياً — عرض نموذج 3D لمعلم سياحي عبر AR على الجوال أو المتصفح | 4-6 أسابيع (POC) |
| **التعرف على المعالم (Landmark Recognition)** | متوسطة — تتطلب قاعدة بيانات صور/نماذج للمعالم + تعرف بصري | 8-12 أسبوع |
| **الملاحة بالواقع المعزز في الشارع** | صعبة — تتطلب بيانات جيومكانية دقيقة (ARCore Geospatial API / Apple's equivalent)، وتغطيتها محدودة جغرافياً | 12-16 أسبوع |
| **معاينة غرف الفنادق بـ AR** | صعبة تشغيلياً (وليس تقنياً) — تتطلب تصوير/مسح كل غرفة فندق فعلياً (تعاون مع الفنادق) | يعتمد على عدد الفنادق الشريكة |

**التوصية**: نبدأ بميزة واحدة فقط (معاينة الوجهة) كبرهان مفهوم (POC) في مدينة
واحدة تجريبية، قبل التوسع.

---

## 2. الخيارات التقنية

### للويب (تجربة سريعة بلا تثبيت تطبيق)
- **WebXR Device API** + **model-viewer** (Google) أو **three.js** لعرض نماذج
  3D بصيغة glTF/GLB مباشرة من المتصفح.
- يعمل على أندرويد (Chrome) بشكل جيد؛ الدعم على iOS Safari محدود — عادة
  نستخدم **AR Quick Look** من Apple كبديل (يفتح نموذج USDZ في تطبيق منفصل).

### للجوال (تجربة أصلية كاملة)
- **iOS**: ARKit + RealityKit (Swift) — يتطلب كود Swift أصلي، حتى داخل تطبيق React Native.
- **Android**: ARCore + Sceneform/Filament (Kotlin) — نفس الأمر، كود Kotlin أصلي.
- **الجسر مع React Native**: مكتبة مثل **ViroReact** أو وحدات أصلية مخصصة
  (Native Modules) نربطها بتطبيق Expo عبر **Expo Config Plugins** أو
  **Expo Development Build** (لا تعمل ميزات AR في Expo Go العادي — تحتاج
  "custom dev client").

### خط أنابيب المحتوى ثلاثي الأبعاد
- تصميم/مسح النماذج (Photogrammetry لمعالم حقيقية، أو نماذج مصممة يدوياً)
  بصيغة **glTF** (للويب) و**USDZ** (لـ iOS).
- استضافة النماذج عبر CDN (نفس أسلوب الصور).

### التعرف على المعالم
- **Google Cloud Vision API** (Landmark Detection) كنقطة بداية سريعة بدل بناء
  نموذج تعرف مخصص من الصفر.
- بديل متقدم لاحقاً: نموذج On-device (Core ML / ML Kit) لتقليل زمن الاستجابة
  والعمل بدون إنترنت.

## 3. خطة المراحل (Sub-Roadmap)

### المرحلة 1 — الاستكشاف والبرهان (Discovery + POC), 4-6 أسابيع
- اختيار مدينة/معلم واحد للتجربة (مثلاً معلم واحد مشهور).
- بناء نموذج 3D واحد وعرضه عبر WebXR على الويب + AR Quick Look على iOS.
- لا حاجة لتطبيق منفصل في هذه المرحلة — إثبات فكرة فقط.

### المرحلة 2 — تجربة تجريبية بمدينة واحدة (Pilot), 8-10 أسابيع
- دمج معاينة الوجهة داخل تطبيق الجوال (Expo Dev Client + ViroReact أو
  وحدات أصلية).
- إضافة 5-10 معالم بنماذج 3D حقيقية لمدينة واحدة.
- قياس الأداء (زمن التحميل، استهلاك البطارية، حجم التطبيق).

### المرحلة 3 — التعرف على المعالم, 6-8 أسابيع (بالتوازي مع المرحلة 2 إن توفر فريق إضافي)
- تكامل Google Cloud Vision (Landmark Detection).
- واجهة "وجّه كاميرتك" مع تراكب معلومات عن المعلم.

### المرحلة 4 — التوسع الجغرافي, مستمر
- إضافة مدن/معالم جديدة تدريجياً حسب الطلب الفعلي من المستخدمين، وليس دفعة واحدة.
- إعادة تقييم جدوى ميزتي "الملاحة الشارعية" و"معاينة غرف الفنادق" بناءً على
  نتائج المراحل السابقة — كلتاهما تتطلبان استثماراً تشغيلياً كبيراً (بيانات
  جيومكانية مرخصة، أو تصوير فعلي لآلاف الغرف)، فلا يُنصح بالبدء بهما إلا بعد
  التحقق من أن ميزة AR الأساسية تضيف قيمة حقيقية يستخدمها الناس.

---

## 4. الاحتياجات (فريق + تكلفة تقديرية)
- مطور iOS أصلي (ARKit) بدوام كامل أو تعاقد.
- مطور Android أصلي (ARCore) بدوام كامل أو تعاقد.
- فنان/مصمم ثلاثي الأبعاد (أو خدمة Photogrammetry خارجية للمعالم الحقيقية).
- ميزانية APIs: Google Cloud Vision يُفوتر لكل استدعاء — تقدير التكلفة يعتمد
  على حجم الاستخدام المتوقع.

## 5. مخاطر يجب معرفتها مسبقاً
- تجربة AR ضعيفة (نموذج بطيء التحميل أو غير دقيق) تضر بصورة التطبيق أكثر من
  عدم وجود AR أصلاً — لذلك نبدأ بمعلم واحد مصقول جيداً بدل عشرات المعالم الضعيفة.
- تغطية ARCore Geospatial API محدودة لبعض المدن فقط — يجب التحقق من التوفر
  في المدن المستهدفة قبل الالتزام بميزة الملاحة الشارعية.
- حجم التطبيق يزداد بشكل ملحوظ مع تضمين محركات AR — يجب قياس الأثر على معدل
  التثبيت والاحتفاظ بالمستخدمين.
