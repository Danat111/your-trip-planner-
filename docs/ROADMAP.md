# خارطة طريق تطوير "Your Trip Planner" — من نموذج أولي إلى منتج فعلي

## 0. الوضع الذي بدأنا منه (تشخيص حقيقي بعد فحص الكود)

| البند | الحالة قبل هذا العمل |
|---|---|
| الواجهة الأمامية | موقع تسويقي React جيد التصميم، **لكنه كان لا يُبنى إطلاقاً** (استيرادات خاطئة لثوابت غير موجودة في 9 ملفات + خطأ حساسية أحرف) |
| الأمان | مفاتيح APIs سرية (Amadeus, Google) كانت مكتوبة لتُستخدم مباشرة من المتصفح — ثغرة حرجة |
| "الواقع المعزز" | رسوم توضيحية فقط، لا تقنية AR حقيقية (لا WebXR، لا ARKit/ARCore) |
| "الذكاء الاصطناعي" | منطق توزيع ثابت (تقسيم المعالم على الأيام حسابياً)، ليس نموذج ذكاء اصطناعي فعلي |
| Backend | غير موجود إطلاقاً — لا مستخدمين، لا حجز، لا حفظ بيانات |
| تطبيق الجوال | غير موجود |

## 1. ما تم تنفيذه فعلياً في هذه الجولة

✅ **إصلاح الموقع الحالي بالكامل** — أصبح يُبنى وينجح (`npm run build`) بعد
   إصلاح 9 ملفات معطوبة وخطأ حساسية الأحرف وتعارض إصدارات الحزم.

✅ **Backend حقيقي وكامل** (`/server`) — Node.js + TypeScript + Express + Prisma:
   - تسجيل/دخول بـ JWT وتشفير كلمات مرور (bcrypt)
   - وكيل آمن (Secure Proxy) لكل مفاتيح APIs الخارجية — لا تُكشف للمتصفح أبداً
   - **ذكاء اصطناعي حقيقي**: استدعاء Claude لتوليد خطط رحلات مخصصة فعلياً
     بناءً على الوجهة والتواريخ والميزانية والاهتمامات وبيانات الطقس/المعالم الحية
   - حفظ/استرجاع/حذف رحلات المستخدم (CRUD محمي بالمصادقة)
   - تم تثبيت الحزم والتحقق من أن TypeScript يترجم الكود بدون أخطاء

✅ **ربط الواجهة الأمامية بالـ Backend الآمن** بدل الاستدعاء المباشر غير الآمن.

✅ **هيكل تطبيق جوال حقيقي** (`/mobile`) — Expo/React Native:
   - تنقّل بالتبويبات (الرئيسية، خطط رحلة، حسابي)
   - شاشة تخطيط رحلة تستدعي فعلياً نفس Backend والذكاء الاصطناعي
   - نفس الهوية البصرية (الألوان) المستخدمة في الموقع

✅ **خطة معمارية منفصلة للواقع المعزز الحقيقي** (`AR_ARCHITECTURE.md`) — لأنه
   مشروع كبير بحد ذاته كما اتفقنا.

## 2. خارطة الطريق للمراحل القادمة

### المرحلة 1 (أسابيع 1-3): الإطلاق التقني الآمن
- [ ] نشر الـ Backend على استضافة حقيقية (Render / Railway / Fly.io) مع Postgres بدل SQLite.
- [ ] الحصول على مفاتيح APIs فعلية: Anthropic، Google Places، OpenWeatherMap، Amadeus (اختياري).
- [ ] نشر الموقع (Vercel/Netlify) مع ربط `VITE_API_BASE_URL` بعنوان الـ Backend المنشور.
- [ ] إعداد `_redirects` أو `vercel.json` (موجودة مسبقاً في `routing_fix.md`) لحل مشاكل التوجيه.
- [ ] اختبار شامل لتدفق: تسجيل حساب → توليد رحلة بالذكاء الاصطناعي → حفظها.

### المرحلة 2 (أسابيع 4-8): تجربة مستخدم كاملة
- [ ] شاشات تسجيل الدخول/التسجيل فعلياً في الموقع والتطبيق (الـ API جاهز، الواجهات غير مبنية بعد).
- [ ] صفحة "رحلاتي" لعرض/تعديل/حذف الرحلات المحفوظة.
- [ ] تحسين توليد الذكي: السماح للمستخدم بتعديل يوم معين وإعادة التوليد بدل الرحلة كاملة.
- [ ] تقسيم حزمة الـ JavaScript (الموقع الحالي 558kB في ملف واحد) لتحسين سرعة التحميل.

### المرحلة 3 (أسابيع 9-14): تطبيق الجوال إلى الإطلاق
- [ ] بناء شاشات المصادقة والرحلات المحفوظة في التطبيق (نفس منطق الموقع).
- [ ] اختبار على أجهزة iOS/Android فعلية.
- [ ] إعداد EAS Build للنشر على App Store و Google Play.

### المرحلة 4 (متوازية، أطول أمداً): الحجز الفعلي والدفع
- [ ] اتفاقية شراكة رسمية مع Amadeus (أو مزود حجز بديل) لتفعيل الحجز الحقيقي وليس العرض فقط.
- [ ] تكامل بوابة دفع (Stripe) — يتطلب امتثالاً قانونياً/مالياً حسب الدولة المستهدفة.

### المرحلة 5 (مشروع فرعي منفصل): الواقع المعزز الحقيقي
راجع `AR_ARCHITECTURE.md` — يبدأ بمعلم واحد كبرهان مفهوم، ويتوسع تدريجياً.
لا يُنصح ببدء هذه المرحلة قبل استقرار المراحل 1-3، لأنها تتطلب فريقاً وخبرات
مختلفة تماماً (تطوير أصلي iOS/Android + محتوى ثلاثي الأبعاد).

## 3. مخاطر وقرارات يجب اتخاذها قريباً
- **التكلفة التشغيلية للذكاء الاصطناعي**: كل عملية توليد رحلة تستدعي Claude
  فعلياً (تكلفة حقيقية لكل طلب) — يُنصح بوضع حد أقصى لعدد الطلبات لكل مستخدم
  غير مسجل، وقد تمت إضافة تحديد معدل (Rate Limiting) أساسي بالفعل.
- **جاهزية بيانات الحجز الحقيقية**: بيئة Amadeus المستخدمة حالياً هي `test.api.amadeus.com`
  (بيانات تجريبية) — الانتقال لبيانات حقيقية يتطلب حساب إنتاج معتمد من Amadeus.
- **قرار AR**: يُنصح بعدم الإعلان تسويقياً عن ميزات AR للمستخدمين حتى تكون
  جاهزة فعلياً، تفادياً لتكرار الفجوة بين التوثيق والواقع التي وُجدت في النسخة الأصلية.
